# Spike 3 findings: Notion's access model on per-person sync

**Goal:** check whether Notion's access model ([ADR-NOTE-011](../adr/ADR-NOTE-011-access-control.md), [ADR-NOTE-012](../adr/ADR-NOTE-012-page-permissions.md), the [access specs](../specs/access/README.md)) can be built on this app's stack, Yjs documents synced whole by Hocuspocus with a local copy on every device, when a device may only receive what its person can open ([#11](https://github.com/christiannaths/homelab/issues/11)). Four risks:

1. **Each person's page tree.** A Yjs document reaches a device whole or not at all, so the old spike's single workspace document, which holds every page's title and parent, cannot stay.
2. **Rejecting edits.** A device below Can edit applies an edit locally before the server sees it. The server must refuse it, and the device must not stay out of step or resend it forever.
3. **Startup speed.** More, smaller documents must not make startup and sync much slower at the [ADR-NOTE-004](../adr/ADR-NOTE-004-hosting-and-scale.md) scale (about 2,000 pages, a few people).
4. **Losing access.** At the next sync after losing access, a device deletes its copies, and offers unsynced edits back as a new Private page.

**Result: all four hold.** The decisions are recorded in [ADR-NOTE-013](../adr/ADR-NOTE-013-data-layout.md) (the document split), [ADR-NOTE-001](../adr/ADR-NOTE-001-offline-use.md) (rewritten in place), [ADR-NOTE-010](../adr/ADR-NOTE-010-sync-and-access-checks.md) (rewritten in place), and [ADR-NOTE-011](../adr/ADR-NOTE-011-access-control.md) and [ADR-NOTE-012](../adr/ADR-NOTE-012-page-permissions.md), now accepted.

## What was built

The spike is [`spikes/notes-access-sync-poc/`](../../../../spikes/notes-access-sync-poc/README.md) (frozen, [ADR-PLAT-003](../../../../docs/adr/ADR-PLAT-003-proof-of-concept-code.md)), started from a copy of the [block editing spike](../../../../spikes/notes-block-editing-collaboration-poc/README.md). Its README says how to run it and how it is organised.

- **Model** (pure TypeScript): the page tree, the access rules (`access.ts`: levels per page and sidebar sections), the update review (`review.ts`), people, teamspaces, sharing, overrides and databases.
- **Server:** Hocuspocus 4.7.1 with SQLite. It keeps a catalog of every page's metadata and access in memory, writes each person's index, checks every document a connection opens and every update before applying it, and re-checks open connections when access changes.
- **Web:** a React PWA with BlockNote and y-indexeddb: a person picker (identity is faked: the token is the person id), Private and Shared sections, a Share panel with inherited entries (each with the page it comes from; entries inherited from above a parent the device doesn't hold can't be listed, and the panel says so), read-only pages below Can edit, recovery from refusals, deletion of lost pages and an offer to keep unsynced edits. There is no web UI for teamspaces or databases; those are covered at the sync boundary. Databases have only text, number and checkbox properties and one table view.
- Versions: Node 26.12, `@hocuspocus/server`/`provider` 4.7.1, Yjs 13.6.33, y-indexeddb 9.0.12, Playwright 1.64.1.

**Tests**, in three seams (all paths below are under the spike):

- **Access rules:** 133 Vitest unit tests in `model/src/`, including convergence tests for every access change and move ([ADR-NOTE-006](../adr/ADR-NOTE-006-merge-safety.md) rule 5).
- **Sync boundary:** 81 tests in `server/testing/`. Each starts a real server process and connects Node clients as different people, then checks which documents each one receives, what the server accepts and what their contents contain.
- **Two-browser:** 16 Playwright tests in `e2e/tests/`, plus the opt-in 2,000-page timing test (`SLOW=1`). They include two people with Can edit editing the same shared page offline, whose edits merge on reconnecting, as before access existed (story 48: "two people with Can edit both edit a shared page offline …" in [`collaboration.spec.ts`](../../../../spikes/notes-access-sync-poc/e2e/tests/collaboration.spec.ts)).

They all pass at the spike's final commit; the e2e suite also passed 48 of 48 with `--repeat-each 3`.

The first ticket (#12) had a sync-boundary test that two people both receive a page one of them created. It held only while everyone could open everything. Once pages were Private by default (#14), the Private-page tests replaced it (a Private page reaches nobody else), and the sharing tests (#15) replaced it for pages that do reach someone else.

## Risk 1: each person's page tree

**Holds.** Every page is its own document, holding its title, place and access beside its content. Each person's tree is built from the page documents they received, and a per-person index written by the server tells devices which documents to open ([ADR-NOTE-013](../adr/ADR-NOTE-013-data-layout.md)).

- **A page carries its own title, parent, section and order** (`meta`), so receiving a page tells a device about that page and nothing else. There is no workspace-wide document: `workspace:default` is refused. Evidence: [`model/src/tree.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/tree.test.ts) ("writes each page's title and place into that page's own document only"), [`server/testing/sync-boundary.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/sync-boundary.test.ts) ("a member's Private pages … never reach anyone else's device: no document, and no title in anything they receive").
- **The index holds ids and levels, not titles.** `index:<personId>` lists the pages and teamspaces the person can open, with their level. Only the server writes it, and only its person can open it, read-only. It is needed because children name their parent, but parents don't list their children. Evidence: [`sync-boundary.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/sync-boundary.test.ts) ("opens a person's own page index read-only", "are refused when someone else asks for them by name, as is their page index"), [`server/testing/rejecting-edits.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/rejecting-edits.test.ts) ("a write to the person's own page index is refused, and the index recovers").
- **The tree is derived, not repaired** ([ADR-NOTE-006](../adr/ADR-NOTE-006-merge-safety.md)). A parent the device never received counts as missing, so the page is top level, in Shared. Moves, renames and creates are ordinary edits to one page document, and converge with no server logic. Evidence: [`tree.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/tree.test.ts) ("concurrent edits under the per-page split": A-under-B against B-under-A, a three-page cycle in any arrival order, a page whose parent a device never receives).
- **A page someone can open below one they can't** arrives alone, at the top of Shared, with a breadcrumb that starts at it. The hidden parent's document and title never arrive. Evidence: [`server/testing/overrides.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/overrides.test.ts) ("arrives at the top of the Shared section with its subpages, and no document or title of the hidden parents"; "stays when the parent it was shared through is unshared"), [`e2e/tests/overrides.spec.ts`](../../../../spikes/notes-access-sync-poc/e2e/tests/overrides.spec.ts) ("a page shared without its parent is at the top of Shared, with a breadcrumb that skips the parent").
- **Access data lives in the page it applies to** (an `access` map in the page document), so it reaches exactly the people who can open the page, works offline and merges like any Yjs data. Devices never work out their own level: it depends on ancestors they may not hold, so they read it from their index. Evidence: [`model/src/sharing.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/sharing.test.ts) ("concurrent access changes"), [`model/src/overrides.convergence.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/overrides.convergence.test.ts), [`e2e/tests/sharing.spec.ts`](../../../../spikes/notes-access-sync-poc/e2e/tests/sharing.spec.ts).
- **Teamspaces and databases fit the same split.** A teamspace is its own document (name, kind, defaults, members), sent only to people who may see its name. A database is a page holding its views, a `schema:` document holding its properties, and one page document per row, so a single row can be shared on its own. Evidence: [`server/testing/teamspaces.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/teamspaces.test.ts) ("a private teamspace … never sends its name or pages to a member who isn't in it"), [`server/testing/databases.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/databases.test.ts) ("someone given only one row receives that row and its values, and nothing else of the database"), [`model/src/database.convergence.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/database.convergence.test.ts).
- **Guests** receive only the pages shared with them and their subpages: no Private section, no teamspaces and never general access. They create pages only below a page they can edit. Evidence: [`server/testing/guests.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/guests.test.ts), [`model/src/guests.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/guests.test.ts), [`e2e/tests/guests.spec.ts`](../../../../spikes/notes-access-sync-poc/e2e/tests/guests.spec.ts).

### Ids that still reach devices

Titles, names and content of what a person can't open never reach their devices. Some **ids** do, as references inside documents they can open:

- **A hidden parent's id**, as the page's own `parentId`. The page's editors need it to write moves. A row given on its own names its database the same way.
- **A teamspace's id, for a guest** given a page from that teamspace, as the page's `section`. The guest never receives the teamspace document, so never its name ([`guests.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/guests.test.ts): "given a page in a teamspace, receive that page but not the teamspace or its other pages", which checks `receivedContent()` for the name).

Both are random UUIDs and reveal only that something exists. The same applies to a page a member hasn't been told about: any member may open a page id the server has never seen, so it can be created there, and this is safe only because ids are random UUIDs ([`model/src/access.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/access.test.ts): "documents that are not existing pages"). [ADR-NOTE-013](../adr/ADR-NOTE-013-data-layout.md) records both.

### Rejected options

Each is in [ADR-NOTE-013](../adr/ADR-NOTE-013-data-layout.md) with its reasons. In short: a filtered tree document per person, written by the server (the server becomes a merge point and writes repairs); one tree document per Private section or teamspace (a restricted subpage's title would still reach everyone in it); a separate `meta:<id>` document per page (doubles the documents, and was the fallback in case of slow startup, which wasn't needed); and access in its own document, in SQLite, or in the index.

## Risk 2: rejecting edits

**Holds.** The server checks every update against the person's level at that moment, refuses it whole, and closes that one document's connection with the reason. The device then throws its copy of that document away and syncs it again ([ADR-NOTE-010](../adr/ADR-NOTE-010-sync-and-access-checks.md)).

- **The app doesn't offer the edit:** below Can edit, the title and editor are read-only, online and offline, because the level comes from the index stored on the device. Evidence: [`e2e/tests/rejecting-edits.spec.ts`](../../../../spikes/notes-access-sync-poc/e2e/tests/rejecting-edits.spec.ts) ("a page shared at Can comment opens read-only, online and offline"; a Can view page is still read-only after the offline reload at the end of "a forged edit from a Can view device is refused …").
- **A forged or stale edit is refused, never reaches anyone, and the device comes back in step and stops resending it.** Evidence: [`rejecting-edits.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/rejecting-edits.test.ts) ("an edit from a device at Can view/Can comment … is refused, and no other device ever sees it"; "leaves the device with the server's copy, still following the page, and it stops resending the edit"; "an edit made offline after being lowered to Can view is refused on reconnecting, and the device recovers"; "nothing refused was stored: after a restart, no device receives any of it"), and [`rejecting-edits.spec.ts`](../../../../spikes/notes-access-sync-poc/e2e/tests/rejecting-edits.spec.ts) ("a forged edit from a Can view device is refused, and the device drops it from memory and storage").
- **A refusal touches one document only:** the socket and the person's other documents stay open and editable. Evidence: "the person's other pages on the same connection stay editable after a refusal" in [`rejecting-edits.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/rejecting-edits.test.ts).
- **Below Full access, changes to `access` are refused.** Evidence: [`sync-boundary.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/sync-boundary.test.ts) ("changing access … is refused from someone with Can edit, though their other edits are kept"), [`guests.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/guests.test.ts) ("below Full access, may not share it").
- **New pages and moves are checked where they land.** A new page needs Can edit where its first update puts it, and Full access there to set any access. A move needs Can edit at the destination, and Full access on the page if it changes anyone's level; this move rule is the spike's choice (see "Choices Notion doesn't document"). Even Full access can't move a page into someone else's Private section. A page's `kind` can't change once it is created, because turning a row into a page would move it out of its database. A new subpage whose parent the server hasn't received yet (both created offline) is placed by its own `section`, as the derived tree places it, and the parent is checked when it arrives. Evidence: [`model/src/review.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/review.test.ts), and "placing a new page" and "moving a page" in [`rejecting-edits.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/rejecting-edits.test.ts).
- **Can edit content** allows rows, their values and their bodies, and refuses the database page, its views and its properties as `structure-refused`. Evidence: [`databases.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/databases.test.ts) ("with Can edit content": "adding a row and editing a value are accepted"; "changing a view is refused, and the device gets back in step"; "changing a property is refused …"), [`model/src/database.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/database.test.ts).
- **Teamspace changes** are checked the same way, then against the teamspace rules (joining, adding members, settings, the last owner). Evidence: [`model/src/teamspaces.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/teamspaces.test.ts) ("changing a teamspace"), [`teamspaces.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/teamspaces.test.ts).

**Why not Hocuspocus's own read-only mode:** it drops a read-only connection's update and answers `SyncStatus(false)`, and nothing else. The provider keeps the edit, `unsyncedChanges` stays at 1 forever, and the edit goes out again in the handshake on every reconnect. Throwing a reason from `beforeSync` closes the document's connection instead, which is a signal the device can act on. The device can't simply revert, because Yjs can't express the inverse of someone else's insertions, and a revert would be the server writing repairs. The spike's design is built around this: the tests above check that the edit is gone and stays gone.

**Cost:** changes to that one document not yet acknowledged when the refusal arrives are lost with the copy, and so is anything sent after the refused update in the same batch. That only happens to a device that sent something it wasn't allowed to, or that edited offline while its access was lowered.

## Risk 3: startup speed

**Holds.** Per-person sync is as fast as the old spike's whole-workspace sync on the same machine, once three bugs in code copied from the old spike were fixed (below). Startup grows with the number of documents a person can open, not with the size of the workspace.

Measured with [`e2e/tests/access-scale.spec.ts`](../../../../spikes/notes-access-sync-poc/e2e/tests/access-scale.spec.ts) (`SLOW=1`), which seeds a 2,272-page workspace into the server's storage ([`server/testing/seed.ts`](../../../../spikes/notes-access-sync-poc/server/testing/seed.ts), checked by [`seed.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/seed.test.ts)): Private pages for Olive (workspace owner) and Max (member), an open and a private teamspace, two databases of 300 and 100 rows, and pages and rows shared with Max and with a guest, Gus.

- **Setup:** headless Chromium 141 driven by Playwright 1.64 (which expects Chromium 156; it worked, but treat this as a caveat on the numbers), localhost, a shared 4-core container with a load average of 3 to 7 from other agents' browsers.
- **Samples:** each scenario 3 times per run, in 3 runs: 9 samples, shown as **median (min–max)**.
- **Baseline:** the old spike's gate test ([ADR-NOTE-010](../adr/ADR-NOTE-010-sync-and-access-checks.md), `SLOW=1`, 2,001 documents on one device), run interleaved on the same machine; 3 samples from its 3 passing runs.

| Scenario | [ADR-NOTE-010](../adr/ADR-NOTE-010-sync-and-access-checks.md) gate | Old spike, same machine (n=3) | Olive: owner, 1,973 docs | Max: member, 1,252 docs | Gus: guest, 31 docs |
| --- | --- | --- | --- | --- | --- |
| New device downloads everything it can open | 9.4 s | 7.3 s (7.2–8.0) | **5.8 s** (5.5–6.8) | 3.7 s (3.5–4.0) | 0.5 s (0.4–0.6) |
| Reconnect until everything has re-synced | 1.7–2.0 s | 1.7 s (1.5–2.0), n=9 | **1.7 s** (1.6–2.0) | 0.7 s (0.6–0.9) | – |
| Server restart until both devices have re-synced | 7.5 s | 7.6 s (7.0–8.1) | **4.5 s** (4.1–5.9) for both | 4.1 s (2.4–5.1) | – |
| Warm reload until everything has re-synced | 3.9 s | 6.7 s (3.7–7.1) | **5.9 s** (5.6–6.2) | 3.4 s (3.0–3.6) | – |
| Warm reload until every doc is loaded from IndexedDB (sidebar complete) | – | – | 5.8 s (5.5–6.1) | 3.3 s (3.0–3.5) | – |
| JS heap with every document open | – | 397 MB (176–422) | 176 MB (169–182) | 103 MB (82–106) | 12 MB |

- **Documents per person** (the web app's count / all kinds): Olive 1,973 (her index and 1,972 pages) / 1,977 (plus 2 teamspaces and 2 databases' properties); Max 1,252 / 1,254; Gus 31 / 32. The web app doesn't open teamspace or `schema:` documents (no UI for them), and those 4 small documents don't move the timings.
- **Olive is the like-for-like case.** She is within the gate on new device, reconnect and restart. Her warm reload is 5.9 s against the 3.9 s gate, but the old spike itself takes 6.7 s (3.7–7.1) on this machine, so the gap is the machine, not the access model.
- **Startup scales with what a person can open:** Olive's times are about twice Max's, matching her document count, and a guest with 31 documents starts in 0.5 s. A Node device with no storage (protocol and server only) syncs everything in 3.1 s for Olive, 1.8 s for Max and 0.1 s for Gus.
- **Server start** (a catalog of 2,276 documents, then every index): 1.0 s (0.9–4.0, n=12).
- **Nothing was dropped.** After every phase of every run: no socket closed while syncing or reloading, the server held a connection for every document of each device, nothing was refused, Hocuspocus logged no "closing connection", and a rename made after the phase reached both devices.
- **What drives the time is the cost per document:** per-document auth and sync in Hocuspocus, and one IndexedDB database per document on the device (native time was the largest item in the browser profile after the fixes). The access checks themselves cost little once lookups used a map (`pageById`), which saved about 0.25 s of server CPU per full resync of 2,000 documents. What remains in the server profile is Hocuspocus's own work per document.
- **Not measured:** an iPhone (out of scope; desktop Chromium has far more memory, so these numbers don't settle "Keeping every doc in memory" in the [index](../adr/README.md)), a cold offline start, and one person able to open far more than 2,000 documents.

Before the fixes, the first run (Olive, n=3, load average up to 12) gave: new device 8.9 s, reconnect 3.5 s, restart 8.3 s, warm reload 10.6 s.

## Risk 4: losing access

**Holds.** The server, not the index, is the authority: when access changes it re-checks the person's open connections, closes those they lost with `access-revoked`, and makes the rest read-only or writable to match. A device offline at the time finds out on reconnecting, when every document is authenticated again and the lost ones are refused with `no-access`. In both cases the device deletes the document from memory and IndexedDB ([ADR-NOTE-001](../adr/ADR-NOTE-001-offline-use.md)).

- **Pages leave the device and come back when access returns.** Evidence: [`server/testing/losing-access.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/losing-access.test.ts) ("an invite removed: the page and its subpages leave the connected device, and come back when invited again"; "a level lowered to No access: a device that was offline deletes the page when it reconnects"; "a level changed while connected takes effect on the open connection, both ways"), [`e2e/tests/losing-access.spec.ts`](../../../../spikes/notes-access-sync-poc/e2e/tests/losing-access.spec.ts) ("an invite removed while the device is online: the page and its subpages leave its storage, and come back when invited again").
- **Restricting a subpage to No access** removes it and everything under it, title included, and Restore inherited access sends it again. Evidence: [`overrides.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/overrides.test.ts) ("restricting a person to No access on a subpage, then restoring"), [`overrides.spec.ts`](../../../../spikes/notes-access-sync-poc/e2e/tests/overrides.spec.ts).
- **Moves change who has a page.** Moved under a parent the person can't open: it stays if it has an invite of its own (at the top of Shared), and leaves otherwise. Moved into a teamspace the person isn't in: it leaves. Moved to Private: everyone else loses it, the page's own invites included, while explicit invites on its subpages stay, which is what Notion does (story 44). Evidence: "moves" in [`losing-access.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/losing-access.test.ts), [`model/src/losing-access.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/losing-access.test.ts) ("moving a page to Private"), [`losing-access.spec.ts`](../../../../spikes/notes-access-sync-poc/e2e/tests/losing-access.spec.ts) ("moving a page to Private asks first, then takes it off everyone else's devices").
- **Databases:** losing a database takes its rows and properties with it, and losing the only row someone has also takes the properties. Evidence: "a database lost …" in [`losing-access.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/losing-access.test.ts), "unsharing the only row someone has also closes the database's properties on their device" in [`databases.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/databases.test.ts).
- **Unsynced edits are offered back as a new Private page.** The device remembers which documents hold unacknowledged edits (in localStorage, so it survives an offline reload). When one of them is lost, it keeps the last copy and offers it as a new Private page with the lost page's title and content, but not its access. It is the whole page as the device had it, not just the edits, because a Yjs update can't be split back into "the server's" and "mine", and the person could already read the page. Evidence: [`losing-access.spec.ts`](../../../../spikes/notes-access-sync-poc/e2e/tests/losing-access.spec.ts) ("access removed while the device is offline with unsynced edits: on reconnecting it says so and offers them as a new Private page"), [`model/src/losing-access.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/losing-access.test.ts) ("copies the blocks, and none of the lost page's metadata or access").
- **Removing a person** closes all their connections and refuses their index from then on, so their device deletes everything and returns to the picker. **Switching person** on a device deletes the previous person's data too, after asking if anything is unsynced. The spec doesn't ask for this: it was added in #21 so that the next person on a shared device can't read what the previous one could open. Evidence: "a removed person's clients are refused …" in [`losing-access.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/losing-access.test.ts); "a removed person's device deletes the workspace's pages at its next sync" and "switching person deletes the previous person's pages from the device" in [`losing-access.spec.ts`](../../../../spikes/notes-access-sync-poc/e2e/tests/losing-access.spec.ts).
- **A device keeps pages created offline** that aren't in its index yet: it reopens every document still in IndexedDB, and the server's answer decides what is deleted. So a removed person's device only learns about the removal if the server still answers it. With real sign-in ([ADR-NOTE-009](../adr/ADR-NOTE-009-identity.md)), a removed person's session must keep reaching the server long enough to be told "no access", or their device keeps the data.

## Model questions the spike settled

- **Most permissive wins across sources, and a per-person No access does not beat general or teamspace access**, as in Notion ([ADR-NOTE-012](../adr/ADR-NOTE-012-page-permissions.md)). Evidence: [`model/src/overrides.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/overrides.test.ts) ("most permissive wins across sources").
- **Open teamspaces are readable by members who haven't joined**, at the teamspace's non-member level (Can view, Can comment or Can edit; there is no None), as the Notion check found ([`06-notion-access-verification.md`](06-notion-access-verification.md), item 6). Evidence: [`teamspaces.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/teamspaces.test.ts) ("sends its pages to members who haven't joined, readable at the non-member level").
- **Workspace owners receive private teamspaces' names, but not their pages unless they are members.** This settles item 8 of the Notion check for per-person sync. Evidence: "sends its name, but not its pages, to the workspace owner" in [`teamspaces.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/teamspaces.test.ts).
- **Teamspace owners always have Full access** on its pages; no default or page override lowers it. Evidence: "owners keep Full access on its pages …" in [`teamspaces.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/teamspaces.test.ts).
- **Access changes converge** like any other edit, including a move racing a restriction, and an invite added offline while the page moves to Private. Evidence: [`overrides.convergence.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/overrides.convergence.test.ts), [`sharing.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/sharing.test.ts), [`model/src/losing-access.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/losing-access.test.ts).

The differences the Notion check found in the [access specs](../specs/access/README.md) are now applied to them.

## Surprises

### Hocuspocus 4.7.1

- **Authentication runs once per document**, not once per socket, and again for every document on every reconnect. That made per-document authorization free to add, and made the original [ADR-NOTE-010](../adr/ADR-NOTE-010-sync-and-access-checks.md)'s "authentication runs once per connection" untrue of Hocuspocus itself.
- **A per-document close loses its code:** the device always sees 1000, and only the reason gets through. Every refusal and revocation is therefore told apart by its reason (`read-only`, `access-revoked`, …). Evidence: the refusal and revocation tests above, which assert on the reason.
- **Reopening a document straight after destroying its provider breaks:** the new Auth reaches the server's old, still-closing connection. Every provider uses `sessionAwareness: true`, which gives each provider its own key on the socket. Evidence: "sends it to her again on Restore inherited access, on a new device and on the connected one" in [`overrides.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/overrides.test.ts), and the come-back-when-invited-again tests in [`losing-access.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/losing-access.test.ts).
- **The unload race.** A direct connection's `disconnect()` unloads the document at once. A device opening that document in the same moment was attached to the destroyed `Document`, an orphan outside `hocuspocus.documents`, and never again received index changes or closes. It failed about 1 run in 8 of the removal test ("a removed person's clients are refused …" in [`losing-access.test.ts`](../../../../spikes/notes-access-sync-poc/server/testing/losing-access.test.ts)). The server's index writes now use `disconnect({ unloadImmediately: false })`. The window still exists at the debounced unload, but is no longer tied to writes. It wasn't seen again in 18 liveness checks across the final timing runs, nor in the e2e repeats. It may explain earlier one-off flakes.
- **To report upstream** (not reported from the sandbox):
  - the unload race above;
  - `connect()` returns early while the status is Connected, and `checkConnection` never times out a socket that hasn't received a first message. One device stayed "connected" with 0 of 596 documents synced for 10 minutes after a hung close (bug 1 below);
  - `getPendingDocumentCount` is O(n) per document, so O(n²) per connection, visible in the server profile at 2,000 documents;
  - the per-document close code is dropped;
  - a read-only connection's update is answered `SyncStatus(false)` with nothing else, so the provider stays diverged and resends it on every reconnect.
- y-indexeddb 9.0.12's `clearData()` doesn't await the database delete. The spike awaits `destroy()` and then `clearDocument(name)`.

### Three bugs in code copied from the frozen spike

The timing test found these in the web sync code copied from [`notes-block-editing-collaboration-poc`](../../../../spikes/notes-block-editing-collaboration-poc/README.md). They are fixed in this spike only: **the frozen spike still has all three**, and the real app's sync layer must not copy them. Each is guarded by the after-every-phase checks in [`access-scale.spec.ts`](../../../../spikes/notes-access-sync-poc/e2e/tests/access-scale.spec.ts).

1. **Going offline could leave the badge on "Synced" for about 36 s** (about 1 offline switch in 3). `socket.disconnect()` only starts the WebSocket's closing handshake, which can't finish without a network, and the provider says "connected" until the `close` event. `SyncManager.goOffline` now dispatches `close` on the socket itself. **This is also why the old spike's [ADR-NOTE-010](../adr/ADR-NOTE-010-sync-and-access-checks.md) gate test fails now and then:** it failed 2 of 5 runs here on exactly this, the `sync-badge` `/Offline/` timeout.
2. **A read-only document could stay "Syncing" forever after a reload** (about 1 reload in 5, always the person's index). The provider was created before IndexedDB had loaded, so a stored copy that landed after the handshake went out as a live update, which a read-only connection answers with `SyncStatus(false)`. Providers are now created once the local copy has loaded. As a bonus, the handshake's state vector then tells the server what the device has, and the server stops sending every document in full on each start.
3. **Startup was quadratic.** Documents finish loading one task at a time, and on each one the sidebar rebuilt the whole tree and re-rendered every row, and the sync badge recounted every document. Both now publish at most every 100 ms during a burst. Olive's warm reload went from 19.7 s to 5.9 s, and her new device from 11.0 s to 5.8 s.

### Flaky tests, root-caused

- **The e2e helpers raced routing.** A click followed at once by filling `page-title` could land in the previous page's title under load. Reproduced by delaying `hashchange` 300 ms, and fixed by waiting for the new page's view (`openNewPage` in `e2e/tests/helpers.ts`).
- **The People form** cleared the next typed name when the previous add resolved (seen once in 48 runs), and was fixed in `PeopleView`.
- A server race where a page created during an index write was "revoked" from its own creator (about 1 run in 9) was fixed by reading the catalog's current levels.

## Choices Notion doesn't document

The spike had to choose in places where Notion's help centre says nothing. They are recorded here, in the specs and in "Not decided yet" in the [index](../adr/README.md), for a product decision:

- **Moves (a spike choice):** the destination needs Can edit, so even Full access can't move a page into someone else's Private section or under a page the mover can only view; Can edit may move a page only where nobody's access changes; any move that changes someone's level needs Full access on the page ([`review.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/review.test.ts)).
- **Databases:** a Can edit content person can trash rows (a row's `deletedAt` is row data), and the database page's own body counts as structure ([`database.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/database.test.ts)).
- **Guests:** a guest's new subpage inherits its parent's level rather than giving them Full access, and nothing stops a guest with Full access from setting general access on a shared page ([`guests.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/guests.test.ts)).
- **Workspace owners and teamspaces:** they may only toggle a teamspace's default flag and leave; in Notion they can manage every teamspace's settings and members ([`teamspaces.test.ts`](../../../../spikes/notes-access-sync-poc/model/src/teamspaces.test.ts)).
- **Select properties were left out:** with single-row sharing, a select's option names would reach someone given one row.

## Not done or not verified

- **No web UI for teamspaces or databases**; those are tested at the sync boundary, and the web's deletion and recovery code is generic over document kinds.
- **Identity is faked.** Real sign-in ([ADR-NOTE-009](../adr/ADR-NOTE-009-identity.md)) still has to carry the person to each document's authorization.
- **iPhone memory and storage**, cold offline start, and workspaces far beyond 2,000 documents per person (see above).
- **Comments** don't exist, so Can comment behaves like Can view throughout.

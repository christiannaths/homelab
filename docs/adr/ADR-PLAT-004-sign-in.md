# ADR-PLAT-004. How do people sign in to the homelab's apps?

- Status: Accepted
- Date: 2026-10-23
- Depends on: [ADR-PLAT-002](ADR-PLAT-002-repo-structure.md)
- Dependency of: [ADR-ENCY-004](../../apps/encyclopedia/docs/adr/ADR-ENCY-004-identity.md), [ADR-NOTE-004](../../apps/notes/docs/adr/ADR-NOTE-004-hosting-and-scale.md), [ADR-NOTE-009](../../apps/notes/docs/adr/ADR-NOTE-009-identity.md), [ADR-NOTE-014](../../apps/notes/docs/adr/ADR-NOTE-014-http-and-accounts.md), [ADR-PLAT-008](ADR-PLAT-008-work-previews.md)

## Context

The homelab runs several apps for the same few people, on a home server reachable from the internet behind a reverse proxy that terminates HTTPS. Signing in should work like a Google account: one homelab account, one sign-in for every app, and one sign-out that signs the browser out of every app at once. The homelab admin decides, person by person, which apps each person can use and at what level. Passwords, rate limiting and session revocation are security-sensitive code that no app should have to own on its own. Only people already in should be able to bring someone new in: there is no public sign-up. The sign-in pages are part of the homelab, so they must look like it, show at once and ask nothing the homelab does not need.

## Decision

- **The homelab's own accounts service holds the homelab account**, at `accounts.<domain>`, where people sign in and manage their account. It is the app [`apps/accounts/`](../../apps/accounts/server) ([ADR-PLAT-002](ADR-PLAT-002-repo-structure.md)), a Node server built on Better Auth, pinned to an exact version, with one SQLite file. Better Auth keeps the accounts, their passwords and their sessions; the service owns everything around it: the pages, App access and the gateway's answer.
- **People sign in with their email and password.** Emails are stored lowercase and match in any letter case. Better Auth's own sign-up is turned off: accounts are made only by the service itself, from an invite, or from the loader for test people (below) in tests, dev and previews.
- **Every app sits behind one gateway that asks the accounts service about each request** (the gateway's forward auth):
  - Each app is served at the root of its own subdomain directly under one parent domain (`notes.home.example`), with the accounts service at `accounts.` and Home at `home.`. An app on its own origin keeps its offline data, storage and service worker its own, and bundled apps expect to be served at the root of an address, not under a path. The session cookie is set on the parent domain, so one sign-in covers every app and one sign-out ends it for all of them.
  - Before passing a request on, the gateway sends it to the accounts service's `/api/authz/forward-auth`. The service answers 200 with the person in `Remote-User` (their account id), `Remote-Name`, `Remote-Email` and `Remote-Groups`, always all four. With no session it sends the browser to its sign-in page with the app's address to return to. A person without App access to the app gets the service's own 403 "no access" page, on the app's address, and nothing reaches the app. A hostname that is not one installed app directly under the parent domain is refused the same way.
  - The gateway deletes any `Remote-*` headers the browser sent before asking, so no browser header reaches an app whatever the answer holds.
  - The answer is worked out from the database on every request, with no cookie cache, so taking an app away or ending a session takes effect on the person's next request.
  - An app's web app manifest (`/manifest.webmanifest`) and its icons (`/icons/*`) skip the check and are readable without signing in, so Home and the accounts service can learn every app's name and icon by themselves, before anyone has opened the app. Every app keeps them at these paths, so one rule covers every app, and nothing else about an app is readable signed out. The `Remote-*` headers are deleted on these requests too.
  - An app's manifest marks it as opening offline with the homelab member `"homelab": { "opens_offline": true }`. An app without it counts as not opening offline.
  - Only the gateway reaches the apps and the accounts service: none publishes a port of its own.
  - The gateway is the homelab's own build of Caddy ([`packages/gateway`](../../packages/gateway/README.md)): Caddy 2.10.2 with the homelab's module for the App switcher, every version pinned. Each app's site imports two snippets: the sign-in check and the App switcher.
- **Apps have no sign-in code.** An app reads the person from the gateway's headers on each request and keeps no session of its own. It identifies a person by their account id (`Remote-User`), which never changes, never by email or name, which can.
- **App access is the admin's grant of one app to one person, at a level:**
  - It is stored as its own records in the accounts service (person, app, level), with the level `member` or `admin`. `Remote-Groups` lists it as `<app>` for a member and `<app>-admins` for an admin, the app being its subdomain.
  - Only installed apps can be granted or answered for. The install names them in one setting, `HOMELAB_APPS` (for example `notes,encyclopedia`), and App access to any other app is refused.
  - The app decides what its levels mean, from `Remote-Groups`.
  - Being a homelab admin is a flag on the person, which lets them manage people. It adds nothing to `Remote-Groups` and opens no app: a homelab admin is given each app like everyone else.
- **Home is open to every account**, with no App access needed. It lists each person's apps from their App access and from each app's manifest, which it reads itself, so an app shows up before anyone has opened it and apps never report themselves to Home.
- **Sessions last a year** (Better Auth's session expiry), extended in the database when the person uses them a day or more after the last extension. The cookie is `HttpOnly` and `Secure`, on the parent domain.
- **Sign-in attempts are rate limited per address**, the address the gateway saw: the service reads the last `X-Forwarded-For` entry, which the gateway sets, so a browser cannot pick a fresh limit by sending its own. The window and the number of attempts are settings (`SIGN_IN_RATE_WINDOW`, `SIGN_IN_RATE_MAX`).
- **A return address must be https under the parent domain**, or the person lands on their account page, so the sign-in page is not an open redirect. A sign-in form posted from another site is refused.
- **The service's pages are its own**, server-rendered in the homelab look from `@homelab/theme`, following the device's light or dark setting, with no script, loading screen or language picker. They are the sign-in page, the account page, the People page, the join page an invite opens, the "invite can't be used" page and the no-access page. A form on them is a plain HTML form that posts to the service, which accepts it only from its own pages: its `Origin` must be the accounts site, and its `Sec-Fetch-Site`, when the browser sends one, `same-origin`. A homelab app on a sibling subdomain counts as another site, since the session cookie reaches every subdomain.
- **The gateway adds the App switcher to every app's pages, and to the accounts site's.** The switcher is one standalone script, built from `packages/app-switcher` into the gateway's image, and the gateway puts the whole script inline before the last `</body>` of every HTML page an app's site or the accounts site sends, so no app installs anything for it and updating the gateway updates it in every app. It asks Home's `/api/me` for the person and their apps, a cross-origin request that Home allows, with credentials, only for apps under the parent domain. It renders in its own shadow DOM.
  - It is the same in every app, with no options: a small tab hanging from the top centre of the screen, over the page, which pulls the menu down. It never changes an app's layout, so bundled apps look as they are meant to, and it follows the device's light or dark setting. The person's icon takes its colour from their account id.
  - Only a fetch for a whole page gets it (`Sec-Fetch-Dest: document`, `empty` or none): a page in a frame or an embedded object would show a second switcher. An offline-first app's service worker saving its page (`Sec-Fetch-Dest: empty`) gets it too, so the saved page carries the switcher. An HTML download (`Content-Disposition: attachment`) is left as it is.
  - Security policies need no setting per app. When a page limits scripts, in a `Content-Security-Policy` header or a CSP `<meta>` in the page, the gateway adds the switcher's hash, worked out from the script the gateway carries, to the list that limits script elements, and adds every app under the parent domain to the lists that limit requests and images, and `data:` to the image list, so the switcher can reach Home and show the apps' icons, including the ones it keeps. A list that allows every inline script already, with `'unsafe-inline'` and no hash or nonce, is left alone, since a hash would turn that off. A page with no script limit gets no policy added. The switcher styles itself with a constructed style sheet, which style policies do not limit.
  - The gateway changes nothing but HTML pages. It asks upstreams for anything that could be a page without the browser's `Accept-Encoding`, so its proxy asks for gzip and undoes it, and compresses the page again for the browser. It drops a page's `ETag` and `Last-Modified`, so no browser revalidates its way into keeping an old switcher.
  - It works offline, from Home's last answer: it keeps Home's last answer on the device for each app, and shows it when the device is offline or Home cannot be reached. Offline, apps whose manifest does not mark them as opening offline are greyed out, and so are Account settings and Sign out, with "Needs a connection". From another app's page, the gateway's redirect for a signed-out browser fails like an unreachable Home, so the switcher then reads Home's public manifest: Home answering means signed out, and the kept answer is cleared. It asks Home again on every load and when the device comes back online, so access granted or removed meanwhile shows up then. With each answer it keeps the apps' icons too, small, on the device with the answer, so no app's service worker needs to keep them, and a signed-out answer clears them with the rest. Icons load with CORS, which the gateway allows for `/icons/*` from any page, so an error page is never kept as an icon. Home's tiles grey out the same apps offline, and Home's own service worker keeps the icons on its tiles.
- **A person's account page is the accounts site's root**, which the App switcher's Account settings opens. A signed-out browser is sent to sign in and back to it.
  - It shows the person's name, email and the apps they have App access to, each with its level and with the name and icon from its manifest. The service reads the manifests through the gateway with the same reader and rule as Home ([`packages/app-manifests`](../../packages/app-manifests)), and names an app after its subdomain while its manifest cannot be read.
  - The person changes their own name there, which apps see in `Remote-Name` on their next request.
  - The person changes their own password there, with their current password and a new one of at least 8 characters (Better Auth's minimum), with no other rules. The old password stops working at once; the person's sessions on other devices stay signed in.
  - A homelab admin's page links to the People page (`/people`), and nobody else's shows any admin link. The People page refuses anyone who is not a homelab admin.
- **Invites are the only way a person gets an account on a real install.** A homelab admin makes one on the People page for one email, with the App access it grants: only installed apps, each at `member` or `admin`. An email that already has an account is refused. The homelab sends no email, so the page shows the invite's link once, and the admin passes it on themselves.
  - The link is the accounts site's `/join/<token>`, with a random 256-bit token. Only the token's SHA-256 hash is stored, so the database alone cannot be used to join.
  - The join page shows the invite's email, fixed, and asks for a name and a password of at least 8 characters. Joining makes the account with that email whatever the form sends, gives it the invite's App access, signs the browser in and shows the account page. Its form is accepted only from the accounts site's own pages.
  - An invite works once and for a week. The People page lists pending invites, with each one's email, apps and expiry, and an admin can cancel one. A used, expired, cancelled or unknown link shows the "invite can't be used" page (410). Removing the admin who made an invite removes it too.
- **Homelab admins manage people on the People page.** It lists everyone with their name, email and each app they have App access to, at its level, with the app's name and icon from its manifest. From it, any homelab admin can do the following to anyone, themselves included, each as a form that posts to `/people/<account id>/<action>`:
  - Change their App access: give an app, take one away, or change its level. Only installed apps are offered or accepted, each at `member` or `admin`.
  - Turn their homelab admin switch on or off. All homelab admins are equal.
  - Sign them out everywhere, which deletes every session they have.
  - Remove their account, which deletes it with its sessions, its App access and the invites it made. Apps keep what the person made as it is. Their email can be invited again, which makes a new account with a new account id and no App access from before.
  - Each change reaches the person on their next request, since the gateway asks the service about every request and nothing is cached.
  - The service refuses (409) to stop the last homelab admin being one, or to remove them, whoever asks, so the homelab always has a homelab admin. Changes to people run one at a time, so two admins acting at once cannot both pass that check and leave none.
  - Every People page action, the page itself included, refuses anyone who is not a homelab admin (403), sends a signed-out browser to sign in, and refuses a form from another site.
- **The first homelab admin joins with a setup invite.** When the service starts with no accounts, it prints the link of an invite that makes a homelab admin with no App access, replacing any earlier one. Its join page asks for the email too, since nobody has typed one. It stops working as soon as any account exists, so a link left in a log cannot make an admin on a running install.
- **Signing out is a POST to the accounts service's `/sign-out`**, sent by the App switcher's Sign out button, or by the Sign out form on the account page and the no-access page. Apps have no sign-out of their own. It ends that browser's session only: every app in that browser, other open tabs included, is signed out on its next request, and other browsers stay signed in. There is no "are you sure?" step; one can go in the switcher before the POST.
  - The switcher sends it with `fetch` and the browser's cookies, a simple request with no preflight. The service answers 204 with CORS for the page's origin, and the switcher then shows the sign-in page with the page it was on as the return address, so signing in again brings the person back to that app. A form gets a redirect to the sign-in page instead.
  - Only a homelab page can send it. A GET signs nobody out (405), and a POST is refused (403) when the browser marks it `Sec-Fetch-Site: cross-site` or its `Origin` is not an https page under the parent domain, so a link, an image or a form on another site cannot sign a person out.
- **Test people come from one loader** in the accounts service ([`test-people.ts`](../../apps/accounts/server/src/test-people.ts), run as `load-test-people.ts` next to the running service). It makes each person, or brings an existing one to exactly what is given: email, name, published password, homelab admin and App access. With `--only-missing` it makes only the people not there yet and leaves the others as they are. The end-to-end suites use it, and change App access with it. Dev (`tools/dev/`) and every preview (`tools/preview/`, [ADR-PLAT-008](ADR-PLAT-008-work-previews.md)) load the same test people with it on every start, only the missing ones, from [`tools/test-people.ts`](../../tools/test-people.ts).
- **Dev has one-click sign-in links**, one per test person, which sign the browser in with no password. The accounts service answers them at `/test-sign-in` only when started with `TEST_SIGN_IN_LINKS=on`, which only dev's compose file sets, and it refuses to start with it on when `NODE_ENV` is `production`, as in the preview image. Everywhere else the address does not exist.

## Alternatives considered

- **VoidAuth** at `accounts.`, its official image unmodified, answering the same forward-auth request. It was the homelab's sign-in until spec #110. Its pages could not be shaped: their own look, a loading animation, a language picker, an "add a passkey?" question the App switcher had to hide, an unskippable "are you sure?" on sign-out, and sign-in by username. Its admin rights could not be narrowed, so the planned invite service would have had to hold them all.
- **Each app as an OIDC client, with its own device sessions.** Notes was built this way first, on VoidAuth (PR #66). Signing out elsewhere could not reach the apps: VoidAuth's back-channel logout refuses every private, loopback and CGNAT address, which is every homelab address.
- **Each app manages its own accounts,** as Notes first planned with Better Auth. Every app would own password and session security, and a person would have one password per app.
- **Authentik.** It meets every goal, including back-channel sign-out, but needs Postgres, a server and a worker, around 2 GB of memory in practice ([`auth-provider-comparison.md`](../research/auth-provider-comparison.md)).
- **Authelia.** It has no invites or admin pages for people: its users live in a file or an LDAP directory that the admin edits.
- **App access as a comma-separated field on the person**, as in the Better Auth spike. One table of records can be checked, listed and changed one app at a time, and refuses a level that does not exist.
- **Better Auth's cookie cache.** Forward-auth takes about 1 ms per request without it, and with it a removed app or ended session would still open until the cache expired ([`FINDINGS.md`](../../spikes/better-auth-sign-in-poc/FINDINGS.md)).

- The accounts service's in-process tests (`apps/accounts/server/test/`), requests to its Hono app with no gateway or browser: the forward-auth answers for a signed-out browser, a cookie with no session, App access, Home with no apps, a homelab admin, an app taken away, an app no longer installed and hostnames that are not an installed app; the sign-in page and its answers (email in any case, wrong email or password, a form from another site, no public sign-up), the return-address check, a year-long cookie on the parent domain, passwords of 8 characters or more, and rate limiting that a forged `X-Forwarded-For` entry does not get round (issue #111). Sign-out ends one device's session only, answers an app's page with CORS and a form with the sign-in page, and refuses a GET, a cross-site POST and an `Origin` that is missing, `null`, http or not under the parent domain (issue #113).
- The accounts service's in-process tests of the account page: name, email and apps with their level, name and icon from the manifest; a name change in `Remote-Name` on the next request; a password change that needs the current password and 8 characters or more, after which the old password fails; forms posted from another site or a sibling subdomain refused; and the People link and page for homelab admins only. Home's end-to-end suite opens the account page from Account settings, signs a signed-out browser in and back to it, shows the apps' icons read through the gateway, changes a name that Notes then shows, changes a password, and follows a homelab admin's link to the People page (issue #114).
- The accounts service's in-process tests of invites: the link shown once and the invite listed as pending; an invite needing an email and refusing an app not installed, an unknown level and an email that has an account; the join page with the email fixed; joining with the invite's App access, signed in on the account page; the email locked whatever the form sends; one use; expiry after a week; cancelling; a name and an 8-character password needed without using up the invite; forms from another site and non-admins refused on every invite action; and the setup invite making the first homelab admin on an empty install, and nothing once any account exists. Home's end-to-end suite makes an invite on the People page, joins with its link on another device, opens Notes as the new person, and finds a used and a cancelled link showing the "can't be used" page (issue #115).

- The accounts service's in-process tests of dev's sign-in links: a link signs the browser in with the same year-long cookie on the parent domain as signing in, in any letter case, every time, refuses an unknown email and a return address off the domain, and does not exist with the setting off; the setting is refused in production. Loading only the missing people leaves an existing person's password and App access as they were (issue #112).

- The Better Auth spike ([`spikes/better-auth-sign-in-poc/FINDINGS.md`](../../spikes/better-auth-sign-in-poc/FINDINGS.md), PR #109): 11 tests in Chromium through the unchanged gateway, covering one sign-in, refusal and removal of apps, one sign-out per device, forged headers and addresses, invites, passkeys and an authenticator app.

The preview image test reads Notes' and the Encyclopedia's manifests and icons signed out (PR for issue #86).
- Home's server tests (`apps/home/server/test/`) and Home's end-to-end suite: an account with no apps sees only Home, admin levels count, groups with no manifest are skipped, and the homelab admin sees only the apps it was given (PR for issue #87).

- Home's end-to-end suite's sign-out tests: Sign out in the switcher of Home, Notes and the Encyclopedia signs the browser out of every app and another open tab, leaves another browser signed in, and signing in again returns to the app; the account page's and the no-access page's Sign out; and opening the sign-out address signs nobody out (issue #113).
- Home's end-to-end suite's accounts tests: a stand-in bundled app with `default-src 'self'` shows the switcher and its icons with no security-policy errors. The gateway's unit tests cover the policy rules, including `default-src` alone, `'none'`, `'unsafe-inline'` and several policies in one header (issue #103).
- `packages/gateway/test/switcher.test.ts` runs the gateway image in front of a stand-in app: pages get the switcher inline, including service-worker fetches and error pages, and lose their validators; framed pages, scripts, API answers and `HEAD` requests pass through untouched; a page an app compresses itself gets the switcher, and one compressed in a way the gateway cannot undo passes through intact (issue #102); a policy in a header and one in a `<meta>` each gain the switcher's hash, and a page with no script limit gets none (issue #103).
- Home's end-to-end suite's offline tests: after one online visit, Home, Notes and the Encyclopedia open with the network cut and show the switcher, the last list of apps and their kept icons; an app that doesn't open offline and Sign out are greyed out; access granted or removed shows on the next online load and on coming back online; and with Home stopped, the switcher shows the kept answer and icons; kept icons follow apps granted or removed and go on signing out (PR for issue #91, issue #105).
- The ProxyAuth spike ([`spikes/voidauth-proxyauth-poc/FINDINGS.md`](../../spikes/voidauth-proxyauth-poc/FINDINGS.md), PR #68): an offline-first app's service worker and WebSocket through a forward-auth gateway, and a forged `Remote-*` header stopped by deleting those headers first.

## Consequences

- An app trusts whoever sends it the headers, so it must never be reachable except through the gateway. Its tests send the headers themselves. The accounts service likewise trusts the gateway's `X-Forwarded-*` headers, so only the gateway may reach it.
- Adding an app means a site in the gateway that imports its two snippets, its manifest and icons at the fixed paths, and its subdomain in `HOMELAB_APPS`. Nothing changes in Home. A hostname not in `HOMELAB_APPS` is refused for everyone but Home.
- Home and the accounts service reach each app's manifest through the gateway at the app's public address, so the gateway must answer them there, or be named to them by an internal address (`GATEWAY_URL`, with `GATEWAY_CA` for a gateway with its own CA).
- The accounts service must be running for any app request to succeed, including on devices already signed in. An offline-first app keeps working from what it kept on the device.
- The homelab owns the security-sensitive code around Better Auth: the forward-auth answer, App access, rate limiting by the gateway's address, and keeping Better Auth patched. Better Auth is pinned to an exact version, and a security fix is taken by bumping it.
- Forward-auth extends a session in the database, but the gateway passes no refreshed cookie back to the browser, so the cookie keeps the lifetime it got at sign-in until a page of the accounts site refreshes it.
- An offline-first app serves its saved page for every visit, online too, so it shows the switcher from the gateway that saved the page until the app next updates it. The menu's contents stay current, since they come from Home on every load.
- The gateway reads every HTML page into memory to change it, so a page streamed slowly reaches the browser only once it is complete.
- An app learns of a sign-out on its next request. An open WebSocket stays open until it reconnects, and an app opened offline shows what it kept until it is next online.
- The switcher's sign-out needs the accounts service to answer with CORS, so a sign-out the service cannot be reached for leaves the person signed in, and the button says it didn't work.
- Only browsers can use the apps: the service has no tokens for other clients.
- There is no password reset: the service sends no email. Until there is, a forgotten password means removing the account and inviting the person again, as a new account id.
- Removing an account takes one press with no "are you sure?" step, since the pages run no script. A confirmation page can go in front of the POST later.
- An app keeps nothing at `/manifest.webmanifest` or under `/icons/` that is not meant for everyone, since those paths are public. A bundled app's site maps those two paths to its own manifest and icons when one is added.
- In a preview, the accounts service runs in the same container as the gateway, named by `ACCOUNTS_UPSTREAM`. Fly's proxy is the edge there, so the preview's gateway passes on the client address it read from Fly's `X-Forwarded-For` as the only entry, for the rate limit.
- A dev sign-in link is a sign-in with no password, so `TEST_SIGN_IN_LINKS` must never be on where anyone else can reach the homelab.
- Not yet tested: Traefik or nginx as the gateway, and real certificates.

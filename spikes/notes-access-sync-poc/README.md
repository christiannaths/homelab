# Notes: access model on per-person sync (spike)

A throwaway spike for [issue #11](https://github.com/christiannaths/homelab/issues/11): can Notion's access model (Notes [ADR 13](../../apps/notes/docs/adr/0013-notion-style-access.md) and [ADR 14](../../apps/notes/docs/adr/0014-notion-page-access-levels.md)) be built on Yjs documents synced whole by Hocuspocus, when each device may only receive the pages its person can open? It starts from a copy of the frozen [block editing spike](../notes-block-editing-collaboration-poc/README.md), and is left out of repo-wide runs ([ADR 16](../../docs/adr/0016-spikes-stay-out-of-repo-wide-runs.md)).

## Packages
- `model` (`notes-access-sync-poc-model`): pure TypeScript, no DOM. The page tree, the workspace document helpers, the people rules and the **access rules** (`access.ts`).
- `server` (`notes-access-sync-poc-server`): Hocuspocus with SQLite storage, run straight from TypeScript (`node src/index.ts`). Also holds the **sync-boundary** test helpers in `testing/`.
- `web` (`notes-access-sync-poc-web`): the React PWA, with BlockNote and offline storage in IndexedDB.
- `e2e` (`notes-access-sync-poc-e2e`): **two-browser** Playwright tests against real server processes.

## Identity is faked
On a new workspace the app asks for the first person, who becomes the workspace owner. The owner adds members and guests under People. Anyone opening the app picks who they are from a list. The person's id is the connection token, and the server trusts it.

## Where access data lives (#15)
- **The access set on a page lives in that page's own document**, in an `access` Y.Map beside `meta` and `content`: one key per entry, `person:<id>` → level (an invite, or an override of what the person inherits) and `workspace` → level (general access for everyone in the workspace; guests never get it). An absent key inherits from the parent page.
  - It reaches exactly the people who can open the page, who are also the people Notion shows the Share menu to (read-only below Full access). Nobody receives the access entries of a page they can't open.
  - Access changes are ordinary Yjs edits, so they work offline and merge like any other data: invites for different people both survive, and two changes to the same entry end with the same winner everywhere (convergence tests in `model/src/sharing.test.ts`).
  - The sharer's sidebar needs it: a top-level Private page with any invite or general access moves to their Shared section.
- **Each person's levels live in their page index** (`index:<personId>`, id → level), written only by the server. A level depends on ancestors the device may not hold, so devices never work out their own level: they read it from the index to decide what to offer (editing, the Share menu).
- **The server works levels out** from every page's `meta` and `access` (`PageCatalog`, through `model/src/access.ts`), and checks every update before applying it: below Can edit nothing is applied, and below Full access an update that touches `access` is refused (`beforeSync`, `reviewUpdate`, `refuseUpdate`; see "Rejecting edits" below).
- **Rejected:** a separate `access:<pageId>` document (doubles the document count, and the two must always carry the same access); access in SQLite with an HTTP API (not Yjs, so no offline sharing and no merge, against ADR 2); access entries in the per-person index (every sharer's change would be fanned out by the server, and the Share menu needs entries for other people).

## Rejecting edits, and getting back in step (#18)
- **The app doesn't offer the edit.** Below Can edit the title and editor are read-only, online and offline, because the level comes from the person's page index, which is stored on the device like any document.
- **The server still checks every update it receives** (`beforeSync` → `reviewUpdate` in `model/src/review.ts`), whatever the connection was opened as: the live updates and the SyncStep2 a device sends on every (re)connect. It uses the person's level **now**, not the level at open, so a change of access applies to an open connection at once (raising someone to Can edit lets their read-only connection write). Full access is accepted without decoding the update. Otherwise the update is applied to a scratch copy to see what it touches (`previewUpdate`): nothing new is always fine, below Can edit anything is refused, and below Full access a change to `access` is refused.
- **A new page is checked where it is placed.** A page the server has never seen is reviewed as if it already existed where its first update puts it, with no access of its own (`placementLevel`). Creating it needs Can edit there (refused: a page in someone else's Private section, under a page the creator can only view, or content with no `meta`), and any access it sets needs Full access there. A parent the server hasn't seen yet (a subpage created offline before its parent synced) counts as missing, so the page's own `section` decides, as in the tree (ADR 7); the parent is checked when it arrives.
- **A move is checked at both ends** (`reviewMove`): an update that gives an existing page a new `parentId` or `section`.
  - The destination must be a place where the mover could create the page (`placementLevel` at least Can edit). Even Full access can't move a page into someone else's Private section, or under a page the mover can only view.
  - A move that changes anyone's level on the page or below it is a change of access, so it needs Full access on the page where it is now. Moving a shared page into the mover's own Private section is one example; moving it into another shared page is another. Can edit may still move a page where nobody's access changes, such as under a sibling inside the same shared page. (Notion's exact rule here is unverified: record this as the spike's choice.)
  - Updates from Full access are normally accepted without copying the document. A cheap scan of the update (`writesPlacement`) spots one that could write `parentId` or `section`, and only those get the full check.
- **A refused update is refused whole** and closes that one document's connection with the reason (`read-only`, `access-change-refused`, `placement-refused`, `structure-refused` (#20), or a teamspace rule's `teamspace-change-refused`/`last-owner`: the `Refusal` type; teamspace documents go through the same review first, then `refuseTeamspaceChange`). The socket and the person's other documents are untouched. The close message is the signal because Hocuspocus passes only its reason on to the device. Hocuspocus's own read-only handling isn't relied on: it drops the update without saying so, so the device stays out of step and resends it on every reconnect.
- **Recovery: throw the local copy away and sync it again.** A Yjs update can't be taken back, and the device already applied it. On a refusal the device destroys the document's provider, its `Y.Doc` and its IndexedDB store, then opens it again from the server's state (`SyncManager.recover`, the same in the test client). Nothing refused is left anywhere to be sent again. Providers use `sessionAwareness: true` so the reopened provider has its own address on the socket and can't be mistaken for the closing one. The UI follows the replaced document (`onReset`, and a new editor per `generation`).
  - **Cost:** changes made on that page and not yet acknowledged when the refusal arrived are lost with the copy, and so is anything after the refused update in the same batch. That only happens to a device that sent something it wasn't allowed to, or edited offline while its access was lowered. #21 can keep the discarded content and offer it back as a Private page (snapshot it in `recover` before destroying the doc).
  - **Rejected:** keeping the connection open and only answering "not applied" (Hocuspocus's read-only path): the device stays diverged forever. Reverting with an inverse update: Yjs can't express one for someone else's insertions, and it would be the server writing repairs (ADR 7).
- **What this changes in ADR 12:** "authentication runs once per connection" no longer holds. Authorization is **per document**: `onAuthenticate` runs for each document a connection opens (Hocuspocus does this anyway) and decides open, read-only or refused from the access rules; and **per update**: every update is checked against the person's current level before it is applied, so the server is no longer a plain relay of whatever an authenticated connection sends. The session check itself (who the person is) can still be done once per connection and cached.
- **Cost on the server:** one copy of the document per update checked, only for connections below Full access, and for new pages. #22 should measure it on large pages.

## Teamspaces (#17)
- **Each teamspace is its own document**, `teamspace:<id>`: a `settings` map (name, kind, default flag, the members' default level, and on open teamspaces the level for everyone else) and a `members` map (person id → owner or member). One key per field and per member, so concurrent joins and setting changes merge.
- **It reaches exactly the people who may see the teamspace's name**: every workspace member for open and closed teamspaces (read-only for non-members of a closed one), only members and workspace owners for private ones, never guests. Page indexes list the teamspaces a person may open beside their pages, so a private teamspace's id doesn't reach anyone else either.
- **Pages in a teamspace** have the section `teamspace:<id>`. Teamspace owners always have Full access on its pages, which no default or page override lowers (the teamspaces spec, Settings). Top-level pages start from the teamspace's defaults: members get the members' level, and on an open teamspace everyone else in the workspace gets the non-member level as general access (as in Notion: there is no "None", and members who haven't joined still open its pages). A page can override the members' level for itself and its subpages (the page's `access` key `teamspace`), and a change to the teamspace's default reaches every page that doesn't.
- **Changes are checked on the server** before they are applied (`refuseTeamspaceChange`): anyone may join an open teamspace, members add people to closed and private ones, only teamspace owners change settings and roles, only workspace owners make a teamspace default (any kind), and the last owner can't leave. New members are added to every default teamspace by the server.

## Overrides and hidden parents (#16)
- **A per-person entry on a subpage overrides what that person inherits**, for the subpage and everything below it: a higher level expands, a lower one restricts, "none" hides the subtree, and deleting the entry is Restore inherited access. General access overrides the same way.
- **Most permissive wins across sources.** A per-person No access only replaces that person's own entry: it doesn't beat general access (or, later, teamspace access), as in Notion and ADR 14. The Private section's member always keeps Full access.
- **When a person loses a page on the server, the server closes their open connections to it** (reason `access-revoked`), so a restricted page stops reaching a device that already had it. The device deletes its copy (#21, below).
- **A page someone can open below one they can't** arrives alone: their device builds its tree from what it received, so the page is top-level there (in Shared), and the breadcrumb (`breadcrumb()`) starts at it. The hidden parent's document and title never arrive. Its **id** does, as the page's `parentId`: the page's editors write it, and it is a random UUID.
- **The Share menu lists inherited entries** with the page they come from (`shareEntries()`), built from the pages the device holds. Entries inherited from above a hidden parent can't be listed, and the menu says so.

## Databases (#20)
A database is split across documents by who may receive each part, because a single row can be shared on its own (as in Notion), so rows can't live in one document that only arrives whole.
- **`page:<databaseId>`** (kind `database`): the database page's `meta`, `access` and body, plus its **views** (`views` map: view id → sort and filter, one key per setting). Only people who can open the database receive it, so view settings never reach someone given one row.
- **`schema:<databaseId>`**: the **properties** (`properties` map: property id → name, type, order). It reaches everyone who can open the database **or any of its rows** (Can view for the latter), because showing a row needs the property names and types (`schemaAccess`). Devices open it for every database and every row they hold (a row names its database as `parentId`), so the server's indexes don't list it.
- **`page:<rowId>`** (kind `row`, `parentId` = the database): one document per row, with the row's `meta` (its title is the row's Name, `order` its place in the table), its **cells** (`cells` map: property id → value, one key per cell) and its page body. A row is a subpage of its database in the tree, so it inherits the database's access like any subpage and can be shared on its own like any page. Rows aren't sidebar pages (`flattenVisible` doesn't list a database's children); a row whose database the device doesn't hold sits at the top of Shared, like any page below a hidden parent.
- **Can edit content** is Can edit on the database's rows (title, cells, body, order, adding and trashing rows) and nothing on its structure: the database page (title, place, views, body) and its properties are refused as `structure-refused`, and the device gets back in step like any refusal (#18). Adding a row writes only the new row's document, so it never touches the database page. On an ordinary page Can edit content is read-only. A page's `kind` can't change after it is created (turning a row into a page would move it out of its database).
- **Rejected:** all rows' cells in the database document with only row bodies as separate pages (the old spike's model: a row shared alone would carry every other row's values, or none of its own); a properties copy inside every row (fanned out on every property change, and no single place to check structure changes); the properties inside the database page (it would carry the views and the database's title to people given one row).
- **Cost:** one document per row, plus two per database. A 2,000-row database is 2,002 documents, where the old spike had one document plus a body document only for rows with a body. #22 measures what that does to startup.
- Kept small: text, number and checkbox properties (a select's options would show every option name to someone given one row), one table view, no web UI for databases yet.

## Guests (#19)
- **A guest receives only the pages shared with them, and their subpages.** They get no Private section (owning a `private:<guest>` section gives them nothing, `levelOf`), no teamspace documents, never general access ("Everyone in the workspace", including an open teamspace's level for people who haven't joined), and no teamspace ids in their index. A page shared with them out of a teamspace arrives alone: its `section` names the teamspace's id (a random UUID, like a hidden parent's), never its name.
- **A guest creates pages only as subpages of a page they can edit.** They open a page document the server hasn't seen at Can edit, and #18's placement check (`reviewUpdate`, `placementLevel`) decides on the first update. With no Private section and no teamspaces, the only places that give a guest Can edit are inside pages shared with them, so a top-level page is refused with `placement-refused`, and so is a subpage of a page they can only view or comment on.
- **A guest with Full access can share the page**, with other guests too. Below Full access their share is refused, as anyone's is.
- **The sidebar puts a page from a teamspace the device doesn't hold in Shared** (`sidebarSections(tree, me, teamspaceIds)`), so a guest's teamspace page shows up with their other shared pages.

## Losing and regaining access (#21)
- **The server decides, the device obeys.** After each index write the server re-checks that person's open connections (`applyAccessChanges`): a document they can no longer open (page, database properties, teamspace, or everything once they are removed) is closed with `access-revoked`, and any other connection becomes read-only or read-write to match the level now. A device that was offline finds out when it reconnects: every document is authenticated again, and the lost ones are refused with `no-access`. Pages still in IndexedDB but gone from the index are reopened at startup for the same reason, so the server's answer, not the index, is what deletes them (a page created offline isn't in the index yet either).
- **The device deletes what it lost**, from memory and IndexedDB (`SyncManager.lose`). Subpages go too when they lose access, each with its own close; a subpage with an invite of its own stays and moves to the top of Shared. Regaining access sends the page again: it is back in the index, and a fresh document is opened (`sessionAwareness` avoids the reopen race).
- **Unsynced edits are offered back.** The device remembers which documents hold edits the server hasn't acknowledged (localStorage, so it survives an offline reload). If such a document is lost, its last copy is kept and the app offers it as a new Private page, with the lost page's title and content (not its access). It is the whole page as the device had it, not just the edits: a Yjs update can't be split back into "server's" and "mine". Edits refused for being below Can edit (#18) are not offered: the person still has the page.
- **Moving a page to Private removes everyone else's access** (story 44): the move deletes the page's own `access` entries in the same transaction (`movesToPrivate`, `movePage`), so it needs Full access, and the app asks first. Explicit invites on its subpages stay. An invite added concurrently on another device survives the merge, as a later decision.
- **Removing a person** (`DELETE /api/people/:id`, owners only, never the last owner) closes all their connections; their index is refused from then on, so their device deletes everything of theirs and returns to the picker. **Switching person** deletes the previous person's data from the device too (and asks first if anything is unsynced).

## Run it
From the repo root (Node.js 26+):
```sh
npm install
npx nx build notes-access-sync-poc-web
npx nx start notes-access-sync-poc-server   # http://localhost:3000, data in spikes/notes-access-sync-poc/data
```

## Tests
```sh
npx nx run-many -t typecheck test -p 'tag:scope:notes-access-sync-poc'   # unit and sync-boundary tests
npx nx e2e notes-access-sync-poc-e2e   # builds the web app, then runs Playwright
```
Set `PLAYWRIGHT_CHROMIUM_PATH` to use an already-installed Chromium.
